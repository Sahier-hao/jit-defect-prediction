# JIT 缺陷预测系统

> 在**每一次代码提交**的粒度上预测缺陷引入风险，让代码评审员把有限的审查精力优先投向高风险提交。

## 这是什么

**即时软件缺陷预测（Just-in-Time Defect Prediction, JIT）** 是软件工程领域的前沿方向。与传统"按文件／模块粒度"的缺陷预测不同，JIT 在**每次代码提交**的粒度上预测该提交是否会引入缺陷。

**要解决的问题**：当前主流的质量保障手段都有"时机问题"——

| 现有手段 | 局限 |
|---|---|
| 静态代码分析（SonarQube 等） | 基于规则而非历史，无法给出风险概率，误报率高到被开发者忽略 |
| 传统缺陷预测 | 文件／模块粒度太粗，反馈周期按版本计 |
| 代码评审流程 | 没有风险排序，评审员面对 20 个文件的 PR 和 2 个文件的 PR 只能靠直觉 |

**本系统的做法**：从真实开源仓库（Apache ActiveMQ 等 Java 项目）挖掘历史提交数据，用 SZZ 算法构造缺陷标签，提取代码变更度量元训练预测模型，对外提供**带可解释性的在线预测服务**与可视化看板。

**核心价值**：把缺陷拦截在进入主干之前——**质量保障左移（Shift Left）**。

## 核心能力

| 能力 | 说明 |
|---|---|
| **仓库挖掘** | Git 仓库克隆、提交历史解析、缺陷修复提交识别 |
| **缺陷标注** | 基于 SZZ 算法回溯引入缺陷的提交，构造训练标签 |
| **特征工程** | Kamei 14 维代码变更度量元<sup>[1]</sup>，含分散度、规模、目的、历史、经验五组 |
| **多模型预测** | ≥2 类（经典机器学习 + 深度学习）共 ≥8 种模型，支持横向对比 |
| **双维度评估** | Effort-unaware（AUC、F1 等）与 Effort-aware（Popt、Recall@20%Effort 等）两类指标 |
| **可解释预测** | 每个预测结果附带特征归因，说明风险来源 |
| **可视化看板** | 高风险提交列表、缺陷引入趋势、模型性能概览 |

> [1] Kamei et al., *A Large-Scale Empirical Study of Just-in-Time Quality Assurance*, IEEE TSE 39(6): 757–773, 2013.

## 开发规范

本项目采用 **Scrum** 迭代开发与 **OpenSpec 规范驱动开发（SDD）**：

- **分支策略**：`main` 为稳定主干，所有改动走 `feat/` `fix/` `docs/` 等分支 + PR
- **代码评审**：合并前须有至少一位非作者成员 Approve，审阅记录保留在 GitHub
- **规范先行**：先写规范（OpenSpec change），评审通过后再实现；需求变更必须同步更新规格
- **任务追踪**：飞书多维表格看板，任务对应到 Sprint 与 OpenSpec change／task

完整规范见 **[docs/团队协作约定.md](docs/团队协作约定.md)**。
