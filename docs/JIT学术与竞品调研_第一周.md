## 1. 结论摘要

1. `[核心定义]` JIT 缺陷预测以一次代码变更或提交为分析单位，预测它未来是否会诱发修复或缺陷。它可以在代码评审或合并前给出风险排序，但不应被理解为已经确认该提交存在缺陷。
2. `[文献结论]` JIT 已形成较完整的研究脉络：历史修复提交用于构造标签，Kamei 等使用变更级度量构建预测模型，评价同时关注分类效果和评审成本[2][3][4]。深度学习、细粒度定位、在线学习和跨项目学习是后续研究方向[7][8][9][13][14]。
3. `[文献结论]` JIT 的工程可信度高度依赖数据与评价方法。SZZ 可能产生标签噪声[11]，软件演化会带来概念漂移[6][12]，随机划分可能造成时间泄漏，类别不平衡会使准确率失真。因此，系统应展示数据时间范围、标签规则、训练窗口、模型版本和评价指标。
4. `[文献结论]` 深度学习不必然优于传统模型。Zeng 等在扩展数据集上发现，CC2Vec、DeepJIT 并未稳定击败传统 JIT 方法；简单的“新增行数 + 逻辑回归”在部分实验中也有很强表现[10]。因此，先建立经典基线更符合可复现和可解释要求。
5. `[检索结论]` 在本次公开资料检索范围内，Commit Guru 是与课程目标最接近的公开学术工具[5]，但其论文发布较早，本次访问未确认当前站点可用性。CodeScene、Bugspots、Code Maat 以历史热点或代码健康分析为主[20][28][29]；SonarQube、GitHub CodeQL、Snyk Code、Semgrep、Codacy、DeepSource 以静态质量、安全或 PR 检查为主[16][18][21][22][23][24]；CodeRabbit 以 AI 代码评审为主[25][26]；CloudBees Smart Tests 以变更相关的测试选择为主[27]。上述工具并非都与 JIT 构成直接竞争关系。
6. `[项目建议]` 建议的差异化不是宣称“首次提出 JIT 模型”，而是把成熟 JIT 方法组织成一个可运行、可解释、可追溯、可复现的课程产品和交付流程。
7. `[项目建议]` 首轮实现可收缩为一个 Java 开源仓库、一种 SZZ 标签口径、Kamei 14 类特征、按时间划分的数据集、至少两个经典基线、风险列表、提交解释和趋势看板。课程最终要求的“两类、不少于 8 种模型”保留在完整产品 Backlog 中，不必全部纳入首个 MVP。

## 2. 课程要求对本调研的约束

课程文档将 JIT 系统定义为提交级缺陷预测系统，并提出了以下与本调研直接相关的要求：

- 从真实开源仓库，例如 ActiveMQ、Lucene、Hadoop 等 Java 项目挖掘历史数据。

- 提供缺陷概率、缺陷归因或解释，以及风险列表、缺陷引入趋势看板等可视化界面。
- Sprint 0 的交付物必须初步说明目标用户、使用场景、竞品或替代方案、MVP 和实现范围。

## 3. 学术知识梳理

### 3.1 JIT 的准确定义

JIT 缺陷预测是在一次代码提交或变更发生时，预测该变更未来是否会诱发修复或缺陷[2][3][4]。它的输出通常包括：

- 二元结果：该提交是否具有缺陷引入风险。
- 风险概率：该提交为缺陷引入提交的概率。
- 风险排序：将提交按预期收益或风险排序，供评审者优先处理。
- 局部解释：哪些变更特征使风险升高或降低。
- 可选定位：提交中的哪些文件或代码行更值得优先检查。

与传统缺陷预测相比：

| 维度 | 文件/模块级缺陷预测 | JIT 提交级缺陷预测 |
| --- | --- | --- |
| 预测对象 | 文件、类、模块或版本 | 一次提交或代码变更 |
| 预测时机 | 通常在版本发布或迭代节点前 | 代码评审或合并前 |
| 主要用途 | 安排测试和重构资源 | 决定先审哪些提交、合并前拦截哪些风险 |
| 反馈速度 | 较慢 | 快，接近开发者的当前上下文 |
| 主要难点 | 文件粒度和长期演化 | SZZ 标签、时间漂移、评审成本与可解释性 |

### 3.2 从仓库历史到在线预测的标准流程

```text
Git 仓库
  -> 提取提交、作者、时间、变更文件、增删行和消息
  -> 识别修复提交
  -> 用 SZZ 回溯可能引入缺陷的提交
  -> 构造 JIT 样本和标签
  -> 提取 Kamei 14 类特征及可选语义特征
  -> 按时间划分训练、验证和测试集
  -> 训练与调参
  -> effort-unaware / effort-aware 评价
  -> 模型注册与版本化
  -> 在线预测、解释、风险排序和趋势看板
  -> 监控漂移并按新数据重新训练
```

建议在产品文档中使用这条流程作为系统总流程图，并将“SZZ 标签构造”“模型训练”“在线预测”拆成三个边界清晰的模块。

### 3.3 关键算法概念

#### SZZ

SZZ 得名于提出者 Śliwerski、Zimmermann 和 Zeller[2]。其核心思路是先从历史提交中识别修复提交，再分析这些修复涉及的代码行，并借助版本历史寻找可能引入相应代码的历史提交，从而构造缺陷引入标签。不同 SZZ 变体在合并提交、重命名、格式变化和注释处理等问题上采用了不同策略[11]。

常见问题：

- 修复提交识别依赖关键词、Issue 链接或人工规则，可能漏检或误检。
- 移动代码、重命名、格式化、合并提交和多缺陷修复会造成回溯错误。
- 不同 SZZ 变体会产生不同标签，并进一步影响模型性能和特征重要性。
- SZZ 产生的是“可疑缺陷引入提交”标签，不应包装成绝对事实。

产品设计中应记录 SZZ 版本、规则、数据窗口以及无法匹配标签的提交情况。课程 MVP 可先采用一种定义清晰的基础 SZZ，并把其他 SZZ 变体列入后续实验。

#### Kamei 14 类变更度量

Kamei 等使用的 14 个变更特征是 JIT 研究中应用最广的特征集合之一，可分为分散度、规模、目的、历史和经验五组[4]：

| 特征组 | 特征 | 直观含义 |
| --- | --- | --- |
| 分散度 | NS、ND、NF、Entropy | 修改的子系统、目录、文件数量及修改在多文件间的分散程度 |
| 规模 | LA、LD、LT | 新增行、删除行、修改文件在变更前的代码行规模 |
| 目的 | FIX | 该提交是否表现为修复类变更 |
| 历史 | NDEV、AGE、NUC | 历史修改过相关文件的开发者数量、距上次修改的平均时间、相关文件的唯一历史变更数 |
| 经验 | EXP、REXP、SEXP | 开发者的历史提交经验、近期经验、子系统经验 |

这些指标大多可从 Git 历史及其代码快照中获得，可解释性较好，适合作为首个 MVP 的统一特征集。特征名称与含义以 Kamei 等论文及其公开复现材料为准；不同复现实现可能存在细节差异，正式实现时应固定公式和统计窗口。

#### 语义特征与深度学习

- DeepJIT：从提交消息和代码变更中自动学习特征[7]。
- CC2Vec：学习代码变更的分布式表示，并利用提交消息表达变更意图[8]。
- JITLine：强调提交级预测和风险代码行定位，同时讨论 CC2Vec 在严格在线场景中的限制[9]。
- JIT-Smart：把提交级预测和代码行级定位放进同一多任务学习框架[14]。

这些方法适合作为完整产品中的模型对比项，但不应被预设为一定优于经典模型。

### 3.5 评价指标与研究难点

#### effort-unaware 指标

- AUC：衡量风险排序能力，但不能单独说明阈值后的业务效果。
- PR-AUC：在正类占比较低时可以补充 AUC，反映 precision 与 recall 的权衡。
- Precision、Recall、F1：解释告警命中率和缺陷提交覆盖率。
- MCC：在类别不平衡时比 Accuracy 更稳健。
- Brier Score：评价预测概率的校准质量；产品展示“风险概率”时应关注。

#### effort-aware 指标

- Recall@20%Effort：在给定约 20% 评审成本预算时，模型能覆盖多少缺陷引入提交。JIT-Smart 等论文使用这一指标[14]。
- Effort@20%Recall：达到约 20% 的缺陷引入提交召回率需要投入多少相对成本。JIT-Smart 等论文使用这一指标[14]。
- Popt：根据预测分数累积检查变更，并通过归一化成本收益与理想排序、最差排序进行比较。Kamei 等和 JIT-Smart 等论文使用相关成本效益评价[4][14]。
- PCI@20%LOC：JITLine 使用的成本效益指标，把代码行数作为检查成本，并评价在约 20% LOC 成本下的收益[9]。

课程要求同时报告两类指标。建议不要只展示 Accuracy，因为缺陷提交通常远少于正常提交，准确率可能被多数类抬高。不同论文对 effort 的定义和计算实现并不完全一致，报告中必须同时给出指标公式、成本代理变量和计算代码来源，不能直接横向比较名称相同但口径不同的数值。

#### 必须写进设计中的风险

1. 时间泄漏：不能用未来提交训练后回头预测过去提交。主实验应优先采用按时间切分；随机切分只能作为对照，不能替代时间切分。
2. 概念漂移：项目重构、人员变化和业务演化会改变风险规律。系统应支持模型重训、版本切换和性能监控。
3. 类别不平衡：缺陷引入提交通常是少数类，应使用 PR-AUC、MCC、召回率和 effort-aware 指标。
4. 标签噪声：SZZ 结果不是绝对真值，界面应保留“基于历史修复链推断”的说明。
5. 解释不等于因果：特征贡献只能说明模型为何给出分数，不能证明代码本身必然有缺陷。
6. 开发者公平性：避免把模型直接用于个人绩效考核，不建议公开做“低质量作者排名”。
7. 跨项目泛化：不同项目的数据分布差异很大，不能只在一两个仓库上宣称通用。
8. 简单模型的价值：首版应设置逻辑回归或决策树等强基线，深度模型必须与它们公平比较。

## 4. 竞品与类似产品调研

### 4.1 产品分级

- 历史直接方案：Commit Guru 的论文目标与课程产品最接近，即从历史提交构造风险并预测风险提交。其论文声明站点和源代码公开，但本次未确认当前可用性，因此按“历史参考”而非持续运营产品处理。
- 算法基线：DeepJIT、CC2Vec、JITLine、JIT-Smart 等主要贡献是模型、实验方法和复现材料，不应直接等同于面向用户的产品。
- 历史分析替代方案：CodeScene、Bugspots、Code Maat 分析版本历史和工程行为，主要输出热点、代码健康、耦合和趋势；其核心分析粒度通常不是“本提交的缺陷概率”。
- 静态质量与安全替代方案：SonarQube、GitHub CodeQL、Snyk Code、Semgrep Code、Codacy、DeepSource 的核心定位是代码质量、安全或 PR 检查。它们能够与 JIT 系统互补，但不能据其公开定位判定它们采用了 SZZ 或历史缺陷监督学习。
- AI 评审替代方案：CodeRabbit 等直接分析 PR 内容并生成评审意见。其公开定位不是项目历史缺陷概率预测，因此只能进行场景对比，不宜视为同一算法类别。
- 相邻效率工具：CloudBees Smart Tests 公开定位为根据变更选择相关测试，目标是提高测试效率，不是预测提交是否会引入缺陷。

### 4.3 调研结论

1. `[检索结论]` 在本次检索到的公开资料中，与课程目标完全同构且能确认持续维护的产品不多。但这只是本轮检索观察，不能据此断言市场上没有同类产品或商业服务。
2. `[官方资料]` 静态工具主要回答“当前代码触发了哪些质量或安全规则”，JIT 系统则尝试回答“这次变更未来引发修复的可能性有多高”。两者可以集成，但目标和监督信号不同。
3. `[官方资料 + 文献结论]` 历史分析工具主要回答“哪些文件和模块长期值得关注”，JIT 更关注“当前这次提交是否应优先评审”。文件热点可作为 JIT 特征，但不等同于提交级预测。
4. `[检索结论]` 本次检查到的 JIT 研究仓库主要面向论文复现和实验，而不是持续运营的用户产品。其产品化程度应由团队在使用前逐一核验，不宜一概而论。
5. `[项目建议]` 本项目的差异化应落在可运行、可解释、可追溯和可复现，而不是声称首次提出 JIT 算法。是否构成真正市场空白，需要后续用户访谈或更系统的竞品检索才能确认。

## 5. 目标用户与使用场景建议

### 5.1 目标用户

`[项目假设]` 建议将主要用户定义为 Java 开源项目或中小型研发团队中的代码评审者、测试负责人和项目维护者，尤其是希望利用历史提交数据排序评审工作、但没有条件自行维护完整 JIT 研究流水线的角色。

`[项目假设]` 次要用户可以是需要观察缺陷引入趋势、模型效果和质量投入产出的工程负责人。

上述用户定义尚未通过真实访谈验证。Sprint 0 应至少访谈 2-3 名目标用户或由团队成员进行可验证的情境模拟，再决定是否保留全部角色。

### 5.2 核心场景

`[项目建议]` 开发者提交代码或创建 PR 后，系统在评审前对该提交打分。评审者进入“高风险提交列表”，按风险概率、预计评审成本和变更时间排序，查看风险原因、相关文件、模型版本与评价指标，再决定优先审查哪些提交。项目维护者通过趋势看板观察近期风险变化、模型效果和数据质量。

### 5.3 建议的 MVP 边界

首个 MVP 建议包含：

- 接入一个 Java 开源仓库并增量采集提交。
- 构造一种可解释的 SZZ 标签口径。
- 提取 Kamei 14 类基础特征。
- 按时间划分训练集和测试集。
- 训练至少 2 个经典基线模型并比较。
- 输出提交级风险概率和风险等级。
- 提供风险列表、提交详情和基础特征解释。
- 提供缺陷引入趋势看板。
- 展示模型版本、训练窗口和核心评价指标。

首轮不应扩张到：

- 同时支持多个语言和大量仓库。
- 一上线就训练 8 种复杂深度模型。
- 自动阻止合并或替代人工评审。
- 基于作者进行公开排名或个人绩效判断。
- 宣称模型解释就是缺陷因果。

课程要求的“两类模型、不少于 8 种模型”属于最终产品范围。建议将其拆入完整 Backlog：首轮先验证数据链路和两个强基线，后续再加入更多经典模型、集成模型和深度模型。

## 6. 对后续规格与用户故事的输入

`[项目建议]` 以下条目是候选能力，不是已经确认的用户需求。建议在团队评审后，再写入 Sprint 0 的用户故事或 OpenSpec 能力规格：

1. 作为评审者，我可以连接或选择一个 Git 仓库，系统能读取提交历史。
2. 作为数据工程师，我可以查看哪些修复提交被识别，以及 SZZ 回溯得到哪些标签。
3. 作为算法开发者，我可以为重放的数据集提取统一的 Kamei 特征。
4. 作为算法开发者，我可以按时间训练和评估多个模型，并查看模型版本。
5. 作为评审者，我可以按风险概率和评审成本查看待审提交列表。
6. 作为评审者，我可以查看某个提交的风险理由、关键特征和相关文件。
7. 作为项目维护者，我可以查看缺陷引入风险随时间变化的趋势。
8. 作为项目维护者，我可以查看模型指标、数据窗口、标签方法和最近一次训练时间。
9. 作为系统管理员，我可以触发重新训练并保留旧模型用于对比。
10. 作为团队成员，我可以看到模型的不确定性和免责声明，避免把预测当作确定性结论。

这些用户故事还需要团队补齐优先级、验收标准、正常场景、异常场景和边界场景。
