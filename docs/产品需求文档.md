## 三、文档说明

### 3.1 名词解释

| 术语／缩略词 | 说明 |
|---|---|
| **JIT**（Just-in-Time Defect Prediction） | 即时缺陷预测。与传统"文件／模块粒度"的缺陷预测不同，JIT 在**每次代码提交**的粒度上预测该提交是否会引入缺陷 |
| **SZZ 算法** | 一种缺陷标签构造方法，得名于提出者 Śliwerski、Zimmermann 和 Zeller。先从历史提交中识别**缺陷修复提交**，再分析修复涉及的代码行，借助版本历史回溯出**引入缺陷的提交** |
| **缺陷修复提交**（bug-fixing commit） | 提交信息中表现为修复缺陷的提交，通常含 issue 编号或 fix／bug 等关键词 |
| **缺陷引入提交**（bug-inducing commit） | 经 SZZ 回溯认定的、引入了后续被修复代码的提交。**注意：这是"可疑"标签而非绝对事实** |
| **Kamei 14 维** | Kamei 等提出的 14 个代码变更度量元，JIT 研究中应用最广的特征集合，分为分散度、规模、目的、历史、经验五组 |
| **变更度量元** | 描述一次代码变更的量化指标，如修改文件数、增删行数、修改分散程度等 |
| **Effort-unaware 指标** | 不考虑审查成本的评估指标，如 Precision、Recall、F1、AUC，回答"预测准不准" |
| **Effort-aware 指标** | 考虑审查成本预算的评估指标，如 Popt、Recall@20%Effort，回答"同样审查 20% 的提交能拦下多少缺陷"——**本产品价值的直接证据** |
| **Popt** | Effort-aware 评估指标之一。按预测分数累积检查变更，将成本收益与理想排序、最差排序归一化比较 |
| **Entropy** | Kamei 14 维之一，衡量修改在多个文件间的分散程度 |
| **MVP** | Minimum Viable Product，最小可行产品 |
| **Epic／Feature／User Story** | 需求的三级层次：Epic 为业务目标，Feature 为功能模块，User Story 为具体功能点 |
| **SDD**（Specification-Driven Development） | 规范驱动开发，以规范为唯一事实来源，代码是其派生产物 |
| **OpenSpec** | 本课程采用的 SDD 框架，用 Markdown + CLI 管理规范与变更 |
| **Sprint** | Scrum 的迭代周期，本课程每个 Sprint 持续 2-5 周 |

## 四、需求背景

### 4.1 产品／数据现状

#### 4.1.1 问题

软件缺陷发现得越晚，修复成本越高。当前业界的质量保障手段存在一个共同的**时机问题**：

- **传统缺陷预测**是**文件／模块粒度**的——它告诉你"`UserService.java` 这个文件历史上问题多"，但一个文件可能被改过几百次，你仍然不知道**这一次**改动危不危险。
- **静态代码分析工具**（SonarQube、Checkstyle 等）基于**规则**而非历史——它们能发现代码风格和已知反模式，但无法回答"这次提交引入缺陷的概率有多大"，且误报率高，久而久之被开发者忽略。
- **代码评审流程**（GitHub PR Review）本身没有**风险排序**——评审员面对一个 20 个文件的 PR 和另一个 2 个文件的 PR，只能靠直觉决定先看哪个。

结果是：**质量保障的介入时机太晚**（缺陷已进主干），或者**介入时没有优先级依据**（评审精力平均分配）。

#### 4.1.2 解决思路

本系统把预测粒度下沉到**每一次代码提交**：

> 在提交合并进主干之前，预测它引入缺陷的概率，并给出可解释的归因，让代码评审员把有限的审查精力优先投向高风险提交。

这就是**质量保障左移（Shift Left）**——把缺陷拦截在进入主干之前，而不是等到测试阶段甚至线上。

#### 4.1.3 产品价值

- 对**代码评审员**：从"平均用力"变成"重点突破"，在相同审查工作量下拦截更多缺陷。
- 对**团队**：降低缺陷逃逸率，减少后期返工成本。

### 4.2 目标用户

| 角色 | 画像 | 核心诉求 | 使用频率 |
|---|---|---|---|
| **代码评审员**（主要用户） | 团队中负责 Code Review 的开发者，每天要处理多个 PR，审查时间有限 | "告诉我先看哪个提交" | 每天 |
| **算法工程师** | 负责训练、评估、迭代预测模型，关注指标和特征有效性 | "让我快速对比模型、定位特征问题" | 每周 |
| **质量／项目管理者** | 关注项目整体质量走势，需要向上汇报 | "给我看缺陷引入的趋势和分布" | 每周 |
| **系统管理员** | 负责接入新仓库、维护流水线与服务 | "让我低成本接入新项目" | 按需 |

> **依据**：课程要求原文强调"指导代码评审员优先审查高风险提交"，因此**代码评审员**被确定为首要用户，界面设计优先满足其"快速判断"需求，而非算法工程师的"深度分析"需求（R1 评审 Q6 已闭环）。
>
> ⚠️ **本节用户画像为基于课程要求与领域常识的推导，尚未经真实用户调研验证**，见 4.3。

### 4.4 竞品分析

| 方案 | 粒度 | 原理 | 局限 |
|---|---|---|---|
| **SonarQube / Checkstyle** | 文件／代码片段 | 静态规则匹配 | 不利用历史数据；误报率高；无法给出风险概率 |
| **传统缺陷预测研究工具** | 文件／模块 | 代码度量 + 机器学习 | 粒度粗；反馈周期长（按版本）；多为学术原型，无工程化界面 |
| **GitHub / GitLab 原生 Review** | 提交 | 无预测 | 仅提供人工评审流程，无风险排序 |
| **商业代码评审平台**（Reviewable 等） | 提交 | 无预测 | 优化评审**体验**而非评审**优先级** |
| **本系统** | **单次提交** | **历史挖掘 + 机器学习 + 可解释性** | 依赖仓库历史数据质量；冷启动仓库无历史则不可用 |

**差异化定位**：不做又一个静态扫描器，而是**在评审流程中插入一个风险排序层**——用真实开源仓库的历史数据训练模型，对每个提交输出缺陷概率与归因。

> **完整竞品调研**：详见 `docs/JIT学术与竞品调研_第一周.md`（含 16 项竞品／学术方案的对比矩阵、DOI 与官方文档核验依据）及 `docs/JIT竞品对比矩阵.csv`。该调研覆盖 CodeScene、Bugspots、Code Maat、CodeQL、Snyk Code、Semgrep、Codacy、DeepSource、CodeRabbit 等商业与开源方案，以及 Commit Guru、DeepJIT、CC2Vec、JITLine、JIT-Smart 等学术基线。

## 五、需求范围

### 5.1 范围内（MVP 必须交付）

- 支持 **Java 开源仓库**接入：MVP 支持多仓库接入与列表管理，但**训练与评估主链路只保证 1 个主仓库**（以 Apache ActiveMQ 为样本）端到端可复现（见 5.3 A-2）
- Git 仓库克隆与提交历史解析
- 缺陷提交识别 + **SZZ 算法**回溯引入缺陷的提交
- **Kamei 14 维**代码变更度量元计算
- **≥2 类（经典机器学习 + 深度学习）共 ≥8 种**预测模型
- **Effort-aware 与 Effort-unaware** 两类评估指标
- 按时间切分的训练／测试集划分
- Web 界面：高风险提交列表（P0）+ 缺陷引入趋势看板（P1，见 5.3 A-1）
- 在线预测接口（单条 + 批量）与预测解释

### 5.2 范围外（明确不做）

| 不做的事 | 原因 |
|---|---|
| 多语言支持（Python／JS／C++ 等） | 先做透 Java 一种，度量元定义与语言强相关 |
| 代码语义特征提取（如 CodeBERT） | 课程标注为「可选」，资源与时间成本高，列为附加功能 |
| 实时 Webhook 自动接入 CI | MVP 以界面单条查询与批量 API 拉取验证价值，实时接入为附加功能（见 5.3 A-3） |
| 多租户与细粒度权限体系 | 单团队使用场景，投入产出比低 |
| 分布式训练与大规模并发 | 数据规模在单机可处理范围 |
| 缺陷自动修复建议 | 超出"预测"定位，属另一个问题域 |
| 模型自动重训练／定时调度／漂移监控 | MVP 无人值守的线上流量，训练为离线批处理，属运维级能力 |

> **范围控制的判断依据**：课程要求明确警告"项目范围过大、无法在各 Sprint 验收会被要求缩减"。上述范围外项若团队认为仍有余力，应作为**附加功能增量**提出，而非塞进 MVP。

课程要求"至少选择并落实 2 项与项目相关的质量需求"。

| # | 质量属性 | 具体指标 | 验证方式 | 选型 |
|---|---|---|---|---|

| NFR-2 | **可解释性** | 100% 的预测结果附带至少 3 个特征的归因说明 | 接口返回字段校验 | ✅ **已选定** |

> **R1 评审澄清（R1-08）**：NFR-1 与 NFR-2 存在时序冲突——SHAP 等模型无关解释方法对深度学习模型的单次计算耗时可超过 2 秒。为避免自相矛盾的验收，约定：**NFR-1 的计时不含解释计算**；解释结果允许预计算或缓存，**缓存命中时包含解释在内的整体响应仍须 < 2 秒**，缓存未命中时以异步或"计算中"状态返回，不得超时失败。该口径同时写入 Sprint 2 的设计文档。
