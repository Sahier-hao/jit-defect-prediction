## 1. 项目背景与问题陈述

### 1.1 问题

软件缺陷发现得越晚，修复成本越高。当前业界的质量保障手段存在一个共同的**时机问题**：

- **传统缺陷预测**是**文件/模块粒度**的——它告诉你"`UserService.java` 这个文件历史上问题多"，但一个文件可能被改过几百次，你仍然不知道**这一次**改动危不危险。
- **静态代码分析工具**（SonarQube、Checkstyle 等）基于**规则**而非历史——它们能发现代码风格和已知反模式，但无法回答"这次提交引入缺陷的概率有多大"，且误报率高，久而久之被开发者忽略。
- **代码评审流程**（GitHub PR Review）本身没有**风险排序**——评审员面对一个 20 个文件的 PR 和另一个 2 个文件的 PR，只能靠直觉决定先看哪个。

结果是：**质量保障的介入时机太晚**（缺陷已进主干），或者**介入时没有优先级依据**（评审精力平均分配）。

### 1.2 解决思路

**即时缺陷预测（Just-in-Time Defect Prediction, JIT）**把预测粒度下沉到**每一次代码提交**：

> 在提交合并进主干之前，预测它引入缺陷的概率，并给出可解释的归因，让代码评审员把有限的审查精力优先投向高风险提交。

这就是**质量保障左移（Shift Left）**——把缺陷拦截在进入主干之前，而不是等到测试阶段甚至线上。

### 1.3 产品价值

对代码评审员：**从"平均用力"变成"重点突破"**，在相同审查工作量下拦截更多缺陷。

对团队：**降低缺陷逃逸率**，减少后期返工成本。

## 2. 目标用户与角色

| 角色 | 画像 | 核心诉求 | 使用频率 |
|---|---|---|---|
| **代码评审员**（主要用户） | 团队中负责 Code Review 的开发者，每天要处理多个 PR，审查时间有限 | "告诉我先看哪个提交" | 每天 |
| **算法工程师** | 负责训练、评估、迭代预测模型，关注指标和特征有效性 | "让我快速对比模型、定位特征问题" | 每周 |
| **质量/项目管理者** | 关注项目整体质量走势，需要向上汇报 | "给我看缺陷引入的趋势和分布" | 每周 |
| **系统管理员** | 负责接入新仓库、维护流水线与服务 | "让我低成本接入新项目" | 按需 |

> **起草假设**：课程要求原文强调"指导代码评审员优先审查高风险提交"，因此**代码评审员**是首要用户，界面设计应优先满足其"快速判断"的需求，而非算法工程师的"深度分析"需求。

## 3. 竞品与替代方案

| 方案 | 粒度 | 原理 | 局限 |
|---|---|---|---|
| **SonarQube / Checkstyle** | 文件/代码片段 | 静态规则匹配 | 不利用历史数据；误报率高；无法给出风险概率 |
| **传统缺陷预测研究工具** | 文件/模块 | 代码度量 + 机器学习 | 粒度粗；反馈周期长（按版本）；多为学术原型，无工程化界面 |
| **GitHub / GitLab 原生 Review** | 提交 | 无预测 | 仅提供人工评审流程，无风险排序 |
| **商业代码评审平台**（Reviewable 等） | 提交 | 无预测 | 优化评审**体验**而非评审**优先级** |
| **本文系统** | **单次提交** | **历史挖掘 + 机器学习 + 可解释性** | 依赖仓库历史数据质量；冷启动仓库无历史则不可用 |

**差异化定位**：不做又一个静态扫描器，而是**在评审流程中插入一个风险排序层**——用真实开源仓库的历史数据训练模型，对每个提交输出缺陷概率与归因。

## 4. MVP 边界

### 4.1 范围内（MVP 必须交付）

- 支持**单一 Java 开源仓库**接入（以 Apache ActiveMQ 等为样本）
- Git 仓库克隆与提交历史解析
- 缺陷提交识别 + **SZZ 算法**回溯引入缺陷的提交
- **Kamei 14 维**代码变更度量元计算
- **≥2 类（经典机器学习 + 深度学习）共 ≥8 种**预测模型
- **Effort-aware 与 Effort-unaware** 两类评估指标
- 按时间切分的训练/测试集划分
- Web 界面：高风险提交列表 + 缺陷引入趋势看板
- 在线预测接口（单条 + 批量）与预测解释

### 4.2 范围外（明确不做）

| 不做的事 | 原因 |
|---|---|
| 多语言支持（Python/JS/C++ 等） | 先做透 Java 一种，度量元定义与语言强相关 |
| 代码语义特征提取（如 CodeBERT） | 课程标注为「可选」，资源与时间成本高，列为附加功能 |
| 实时 Webhook 自动接入 CI | MVP 用定时/手动触发验证价值，实时接入为附加功能 |
| 多租户与细粒度权限体系 | 单团队使用场景，投入产出比低 |
| 分布式训练与大规模并发 | 数据规模在单机可处理范围 |
| 缺陷自动修复建议 | 超出"预测"定位，属另一个问题域 |

> **范围控制的判断依据**：课程要求明确警告"项目范围过大、无法在各 Sprint 验收会被要求缩减"。上述范围外项若团队认为仍有余力，应作为 **Sprint 3 的附加功能**提出，而非塞进 MVP。

## 5. 用户故事

**优先级定义**：`P0` = MVP 必须交付，缺失则演示不成立｜`P1` = 应该交付，影响产品完整性｜`P2` = 可选增强。

### Epic 1：数据采集与仓库解析

> 业务目标：把真实开源仓库的提交历史变成可训练的、带缺陷标签的结构化数据。

#### Feature 1.1 仓库接入

| ID | 用户故事 | 优先级 |
|---|---|---|
| US-1.1.1 | 作为**算法工程师**，我想要**通过界面填入 Git 仓库地址**，以便系统自动拉取代码历史，而不用手工执行命令 | P0 |
| US-1.1.2 | 作为**算法工程师**，我想要**查看已接入仓库的列表及其状态**（克隆中／解析中／已就绪／失败），以便掌握数据准备进度 | P0 |
| US-1.1.3 | 作为**系统管理员**，我想要**对克隆失败的仓库重试或删除**，以便清理无效数据、释放存储 | P1 |

**US-1.1.1 验收标准**
- WHEN 用户提交一个合法的 Git 仓库地址，THEN 系统创建接入任务并返回任务 ID
- WHEN 用户提交非法地址或私有仓库且无凭据，THEN 系统返回明确错误信息，且不创建脏数据
- WHEN 仓库体积超过设定上限，THEN 系统拒绝并提示上限值

#### Feature 1.2 提交历史解析

| ID | 用户故事 | 优先级 |
|---|---|---|
| US-1.2.1 | 作为**算法工程师**，我想要**系统解析每个提交的元数据**（作者、时间、变更文件、增删行数），以便作为特征计算的输入 | P0 |
| US-1.2.2 | 作为**算法工程师**，我想要**系统自动过滤合并提交与纯格式变更**（如仅改空白、注释），以便减少噪声样本、提升标签质量 | P1 |

**US-1.2.1 验收标准**
- WHEN 解析一个含 N 个提交的仓库，THEN 数据库中产生 N 条提交记录（扣除被过滤项）
- WHEN 某提交的变更文件无法解析（如二进制文件），THEN 跳过该文件且记录警告，不中断整体解析

#### Feature 1.3 缺陷标注（SZZ 算法）

| ID | 用户故事 | 优先级 |
|---|---|---|
| US-1.3.1 | 作为**算法工程师**，我想要**系统自动识别缺陷修复提交**（依据 commit message 中的 issue 编号或缺陷关键词），以便构建初始标签 | P0 |
| US-1.3.2 | 作为**算法工程师**，我想要**系统执行 SZZ 算法回溯出真正引入缺陷的提交**，以便得到训练所需的标签 | P0 |
| US-1.3.3 | 作为**算法工程师**，我想要**查看标注结果统计**（缺陷提交占比、回溯成功/失败数、无法归因的修复提交），以便判断数据质量是否可训练 | P1 |

**US-1.3.2 验收标准**
- WHEN 给定一个已识别的缺陷修复提交，THEN 系统输出被修改的代码行及其对应的引入提交列表
- WHEN 引入提交早于仓库起始或无法定位，THEN 该样本标记为"无法归因"而非错误丢弃，并计入统计

#### Feature 1.4 数据持久化

| ID | 用户故事 | 优先级 |
|---|---|---|
| US-1.4.1 | 作为**算法工程师**，我想要**解析结果持久化到数据库**，以便重复训练时无需重新克隆和解析 | P0 |
| US-1.4.2 | 作为**系统管理员**，我想要**在数据异常时重建指定仓库的数据集**，以便从损坏状态恢复 | P2 |

### Epic 2：特征工程与样本构建

> 业务目标：把原始提交转换成模型可消费的特征向量与标签。

#### Feature 2.1 变更度量元

| ID | 用户故事 | 优先级 |
|---|---|---|
| US-2.1.1 | 作为**算法工程师**，我想要**系统自动计算 Kamei 14 维代码变更度量元**，以便作为模型的标准输入特征 | P0 |
| US-2.1.2 | 作为**算法工程师**，我想要**查看单个提交的 14 维特征明细**，以便核查计算逻辑是否正确 | P1 |
| US-2.1.3 | 作为**算法工程师**，我想要**以插件方式新增自定义度量元**，以便在不改动核心代码的前提下扩展特征集 | P2 |

**US-2.1.1 验收标准**
- WHEN 对一个已解析的提交计算特征，THEN 输出的 14 个维度全部有值，缺失值有明确的填充策略与标记
- WHEN 同一提交重复计算，THEN 结果一致（计算具备确定性）

> **课程对齐**：Kamei 14 维度量元出自 Kamei et al., *A Large-Scale Empirical Study of Just-in-Time Quality Assurance*, TSE 39(6), 2013——课程要求原文引用的文献。

#### Feature 2.2 样本集构建

| ID | 用户故事 | 优先级 |
|---|---|---|
| US-2.2.1 | 作为**算法工程师**，我想要**按时间顺序切分训练集与测试集**，以便模拟"用历史预测未来"的真实场景 | P0 |
| US-2.2.2 | 作为**算法工程师**，我想要**剔除特征不完整的样本**，以便保证模型输入质量，并知道剔除了多少 | P1 |
| US-2.2.3 | 作为**算法工程师**，我想要**查看数据集的类别分布**（缺陷／非缺陷比例），以便判断是否需要处理类别不平衡 | P1 |

**US-2.2.1 验收标准**
- WHEN 执行切分，THEN 训练集的所有提交时间**早于**测试集的任何提交（无时间穿越）
- WHEN 数据量不足以切分，THEN 系统报错并提示最小样本量要求

### Epic 3：模型训练与评估

> 业务目标：训练多类模型并给出可信的对比结论，支撑"选哪个模型上线"的决策。

#### Feature 3.1 经典机器学习模型

| ID | 用户故事 | 优先级 |
|---|---|---|
| US-3.1.1 | 作为**算法工程师**，我想要**一键训练多种经典模型**（逻辑回归、朴素贝叶斯、决策树、随机森林、XGBoost 等，合计不少于 5 种），以便横向对比效果 | P0 |
| US-3.1.2 | 作为**算法工程师**，我想要**调整超参数并重新训练**，以便针对本项目数据优化性能 | P1 |
| US-3.1.3 | 作为**算法工程师**，我想要**查看训练过程日志与耗时**，以便定位慢环节和失败原因 | P2 |

#### Feature 3.2 深度学习模型

| ID | 用户故事 | 优先级 |
|---|---|---|
| US-3.2.1 | 作为**算法工程师**，我想要**训练基于提交变更的深度学习模型**（如 MLP／CNN／LSTM 等，不少于 3 种），以便与经典方法对比 | P0 |
| US-3.2.2 | 作为**算法工程师**，我想要**指定训练轮数与批大小**，以便在可接受时间内完成训练 | P1 |

> **课程对齐**：课程硬性要求"至少 2 类（经典机器学习和深度学习）不少于 8 种预测模型"，故经典 5 种 + 深度 3 种为最低配置，团队可按精力上调。

#### Feature 3.3 评估与对比

| ID | 用户故事 | 优先级 |
|---|---|---|
| US-3.3.1 | 作为**算法工程师**，我想要**查看每个模型的 Effort-unaware 指标**（Precision／Recall／F1／AUC），以便了解整体预测能力 | P0 |
| US-3.3.2 | 作为**算法工程师**，我想要**查看 Effort-aware 指标**（如 Popt、Recall@前 20% 工作量），以便评估在真实审查场景下的实际收益 | P0 |
| US-3.3.3 | 作为**算法工程师**，我想要**查看模型对比表与对比图**，以便快速选出上线模型 | P1 |
| US-3.3.4 | 作为**算法工程师**，我想要**将选定模型保存并登记版本**（含训练数据范围、参数、指标），以便上线使用且结果可复现 | P0 |

**US-3.3.2 验收标准**
- WHEN 生成评估报告，THEN 同时包含 Effort-unaware 与 Effort-aware 两组指标，缺一不可
- WHEN 不同模型使用不同测试集，THEN 系统禁止对比（防止结论失效）

> **课程对齐**：课程要求"评估指标（Effort-unaware 和 Effort-aware 两类）"。两类指标回答不同问题：前者问"预测准不准"，后者问"按风险排序后，同样审查 20% 的提交能拦下多少缺陷"——**后者才是本产品价值的直接证据**。

## 6. 非功能需求

课程要求"至少选择并落实 2 项与项目相关的质量需求"。以下为建议的 4 项，**团队须从中选定不少于 2 项，并在 Sprint 3 给出验证证据**。

| # | 质量属性 | 具体指标（待团队确认） | 验证方式 |
|---|---|---|---|
| NFR-1 | **性能** | 单次预测接口响应时间 P95 < 2 秒；解析 1 万提交规模的仓库 < 30 分钟 | 压测脚本 + 计时日志 |
| NFR-2 | **可解释性** | 100% 的预测结果附带至少 3 个特征的归因说明 | 接口返回字段校验 |
| NFR-3 | **可靠性** | 训练任务失败后可重试且不产生脏数据；服务重启后模型可用 | 故障注入测试 |
| NFR-4 | **易用性** | 新用户从打开界面到完成首次预测 ≤ 5 分钟，无需阅读文档 | 可用性测试（找未参与开发的同学试用并计时） |

> **建议选择 NFR-1 + NFR-2**：NFR-1 有客观数据、易出证据；NFR-2 直接支撑产品核心价值（"可解释"是本系统区别于纯黑盒预测的关键）。NFR-4 证据最易产出（找人试用即可），可作为第三项。
