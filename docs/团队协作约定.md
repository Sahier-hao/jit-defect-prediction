## 二、分支规范

**`main` 是主干，永远保持可运行。任何人不许直接向 `main` 推送。**

| 分支前缀 | 用途 | 示例 |
|---|---|---|
| `feat/` | 新功能 | `feat/repo-clone` |
| `fix/` | 缺陷修复 | `fix/szz-null-label` |
| `docs/` | 文档 | `docs/team-agreement` |
| `chore/` | 配置、依赖、脚本 | `chore/ci-setup` |
| `test/` | 测试相关 | `test/feature-extraction` |
| `refactor/` | 重构（不改行为） | `refactor/parser` |

**规则**
1. 命名全小写，用连字符分隔，**用英文**（避免中文分支名在 CI/脚本中出问题）
2. 分支名要能看出做什么，禁止 `test1`、`aaa`、`update` 这类名字
3. 一个分支只做一件事
4. **合并后立即删除远程分支**（GitHub 合并页有 "Delete branch" 按钮）

---

## 三、提交信息规范

采用简化版 Conventional Commits：

```
<类型>: <简短描述>

<可选正文：为什么这么改>
```

**类型**：`feat` / `fix` / `docs` / `test` / `chore` / `refactor`

**规则**
1. 描述用**中文**，说清"做了什么"，首行不超过 50 字
2. 关联看板任务时在描述末尾带 Issue 编号，如 `feat: 实现仓库克隆 #12`
3. 一次提交只做一件事，禁止 `update`、`修改一下`、`fix bug` 这类无法追溯的信息
4. 正文说明**为什么**，而不是重复标题

**示例**

```
feat: 实现 Git 仓库克隆与提交历史解析

使用 GitPython 解析 commit 元数据，过滤合并提交。
关联 US-1.2.1，见 OpenSpec change add-repo-parsing。
```

## 四、Pull Request 规则

> 课程硬性要求：「合并前应至少有一位非作者成员审阅；审阅意见及修改记录保留在 Git 平台中」。**这是过程分的主要来源。**

1. **一个 PR 只解决一件事**——对应一个分支、一个功能、一个 OpenSpec change
2. **PR 描述必须包含三部分**：
   - 做了什么（对应哪个 User Story / OpenSpec change）
   - 怎么验证（命令、截图或测试结果）
   - 遗留问题（没有就写"无"）
3. **合并前必须有 ≥1 位非作者 Approve**
4. **作者不得合并自己的 PR**——自己开的 PR 由队友点 Merge
5. 审阅人**必须留下意见文字**，不能只点 Approve 了事；至少写一句判断依据
6. 合并方式统一使用 **Merge commit**（保留完整分支历史，便于追溯个人贡献）
7. 合并后删除分支

**审阅响应时限**：PR 提交后 **24 小时内**队友须给出审阅意见（工作日）。

### 建议启用的仓库设置

- **Settings → Branches → 分支保护规则**：`main` 分支开启 *Require a pull request before merging* + *Require approvals = 1*
  开启后无 Approve 的 PR 无法合并，从机制上防止遗漏
- 可选：在 `.github/pull_request_template.md` 放置 PR 描述模板，新建 PR 时自动带出

## 五、会议与汇报节奏

### 每日站会（文字形式）

- **时间**：每个工作日 **21:00 前**
- **形式**：在飞书群发三条，不强制语音会议
  1. 昨天做了什么
  2. 今天计划做什么
  3. 有什么阻塞

> 用文字而非语音，是为了**自动留痕**——这些记录本身是过程证据，也方便写周报时回溯。

### 每周周报

- **提交时间**：每周五晚（放假除外）
- **格式**：`工作周报-YYYYMMDD`，存放于飞书共享文件夹 `04-工作周报/`
- **执笔轮值**：三人轮流执笔，Scrum Master 终审
  | 周次 | 执笔人 |
  |---|---|
  | 第 1 周 | 荀浩 |
  | 第 2 周 | 徐卓航 |
  | 第 3 周 | 杨稳曌 |
  | 第 4 周 | 荀浩（循环） |
- **要求**：「本周计划」须在**周一**填写完成，「本周总结」须附证明材料（PR 链接、文档链接、截图）

### 每周课程汇报

- 每周五课上做简短进展汇报，由 Scrum Master 主讲，其他人补充

## 六、任务与缺陷追踪

### 看板（飞书多维表格）

泳道：`Backlog` → `本周待做` → `进行中` → `待审阅` → `已完成`

- 每个 User Story 拆成的任务都要建卡片
- 卡片字段须包含：关联 User Story ID、负责人、Sprint、状态
- 卡片状态与 GitHub PR 状态保持一致（PR 待审阅时卡片也移到「待审阅」）

### 缺陷管理（GitHub Issues）

- 缺陷使用 Issue 记录，**必须包含**：现象、复现条件、优先级、处理状态、关联提交或 change
- 缺陷修复的分支用 `fix/` 前缀，PR 描述中引用 Issue 编号

## 七、OpenSpec 使用约定

> 课程要求实践规范驱动开发（SDD）：「需求变更必须通过同步新增或修改管理工具及 OpenSpec change 记录，**不得只改代码而不更新规格**」。

1. **一个 change = 一个功能 = 一个分支 = 一个 PR**
2. **先 propose，再实现**——`/opsx:propose` 产出 proposal / specs / tasks 后，经审阅再动手写代码
3. `tasks.md` 中每一项完成后打勾，未完成不得归档
4. **完成后及时 archive**，保持 `openspec/specs/` 与产品实际状态一致
5. 需求变更时：先改需求文档 → 再开对应 change → 最后改代码，**三者不得脱节**

## 八、约定的修改

本约定如需修改，走 `docs/` 分支 + PR，经 ≥1 位非作者 Approve 后合并，并更新文首版本号。
