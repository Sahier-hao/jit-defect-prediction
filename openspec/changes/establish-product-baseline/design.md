## Context

见 proposal 的 Why。当前主规格目录为空；PRD 旧稿的真实评审情况未知，用户明确指出前置工作未完成。CSV 技术试做已有软件检查记录，但没有全量采集、SZZ标签或访谈证据。现有真实来源案例另有保存的修复／集成／issue事件和文件快照，不以小案例代替正式数据集。当前需要的是产品准备和未来行为契约草案。

## Goals / Non-Goals

**Goals:**
- 形成可评审、可追溯的初始产品契约，分开文字完整性与真实确认。
- 用可测正常／异常场景约束数据、模型、预测和解释；保留选型和资源核对任务。
- 让任务、Story、原型及证据相互对应，减少团队从空白文档起步的负担。

**Non-Goals:**
- 本轮不继续业务实现、运行仓库全量采集或建立外部平台；不归档未批准提案。
- 不把固定技术栈、示例分数、候选参数或虚构会议当作已定结果。

## Decisions

1. **先整理准备材料，再逐项核对。** 替代方案是继续按试做代码推导需求，会把已有代码选择误当产品决定。当前以 PRD v0.6 为故事／验收主稿，不重复维护旧8条P0附录。
2. **三层模块化单体作为候选实现。** 详见产品设计 §2。与拆微服务相比，减少新手团队的跨服务协作成本；长任务仍与 API 请求分离，保留持久化 attempt 和恢复状态。
3. **不可变证据与快照。** 标签观察时间、训练截止、schema／清单／模型哈希独立记录；仅提交时间先后不足以证明没有未来标签泄漏。数据库逻辑表和恢复行为见产品设计 §4／§5。
4. **解释有生命周期。** 预测返回状态，最终贡献需真实且带单位；pending 不是已满足解释要求。对性能与解释分别测量，并把可靠性作为第二项质量验证候选。
5. **配置参数与行为约束分开。** 成熟期、切分比例、成本代理、阈值、训练预算的候选值位于设计 §5，需人工核算与数据资源 Pilot。规格约束可追溯、无泄漏和失败不伪装成功，不把待验证数值升级成事实。
6. **首轮与最终模型广度分开。** 首轮一经典基线验证链路，最终覆盖经典／深度两类总计≥8方法。深度输入不能把任意14指标次序当时间序列；候选输入与方法评审后再拆实施 change。

7. **范围收敛与优先级分开。** 保留42条与18/17/7；最终建议24条业务＋2条过程，首轮16条业务。批量API、风险等级、高级筛选、目录图和自动化增量暂缓，不取消基本解析边界、参数／日志留痕和本地规范检查。离线工作页只记录个人草稿，不代表实际平台建板或团队批准。

8. **用真实案例修正数据契约。** [ActiveMQ来源核查](../../../docs/数据核查/ActiveMQ数据可行性核查.md)取得4个历史issue、15份来源，8个边界场景可复核。历史Jira／当前GitHub分开；Fixed不代表Bug；固定分支并保存merge／backport关系；标签截止核对集成和所需历史证据；Kamei与SZZ文件范围分开。没有blame或完整历史，不把修复候选／部分diff度量当正式引入标签／14维训练数据。

## Risks / Trade-offs

- [无真实用户证据] → 调研模板保留支持／反对记录，原型走查后更新范围；不填造支持率。
- [参数和资源未测量] → 显式候选，留下人工核算及 Pilot 任务；不能以1000／50保证统计效力。
- [准备工作被误勾完成] → 全部评审／访谈／实际看板任务保持未完成；文档检查单列，不替代产品验收。
- [历史记录被覆盖] → 保留旧 R1 记载及技术试做证据，增加状态澄清，不更改既有真实技术检查结果。

## Migration Plan

本轮仅调整本地文档和规划，不迁移数据库或归档规格。评审后按选中首轮链路新建实施 change，更新 Story、任务和验收映射；最终归档时才同步已实现／已验证规格。若更换选型，保留旧试做用于对照，迁移和数据保护另行设计。
